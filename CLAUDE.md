# CLAUDE.md — working agreements for AIA

AIA is a research and decision platform: a FastAPI API, a worker that runs durable steps, a
Next.js client, PostgreSQL, deployed to AWS. Before a change that crosses a module boundary, read
[ARCHITECTURE.md](ARCHITECTURE.md); for framework gotchas, [AGENTS.md](AGENTS.md). Start a session
with `python tools/progress.py` to see every plan's status.

These are the project's working agreements, written to help you do your best work. Use judgment.
If a rule gets in the way of doing the job right, say so and propose the change: the agreements
are meant to evolve.

## 0. What matters most

1. **The repository is the memory.** What you learn only survives in code, a test, a doc, or the
   plan file and PR description. A decision explained only in chat gets re-litigated later.
2. **Solid over fast.** When you hit a blocker, ask what the right shape is, not only how to clear
   it. A fix that makes the next three fixes harder is a loss.
3. **Never stamp a guess; prefer null.** And never score *unknown* as *good*: a missing value
   coalesced to a neutral default silently rewards the absence of data.
4. **Finish the job.** If part of the scope is blocked, finish the rest and say exactly what is
   left and why. Scaling the work down is the product owner's call.

## 2. Invariants the code enforces

These are checked by `make layer_check`, the tests or CI. They exist for security, data
protection and research integrity; work with them, and if one is wrong, change it deliberately
in its own PR.

- **Model calls** go only through `GovernedModelGateway.invoke` (ADR 0005). Domain code names a
  `ModelCapability` and a `DataClass`, never a model. No provider SDK in the core or the API.
- **Scope is in the path.** Every project route is `/api/v1/studies/{study_id}/projects/…`; scope
  contexts come only from `ScopeResolver`. Client Knowledge is read inside a resolved scope.
- **Population data** comes only from `PopulationRuntime.load_for_run`; ask
  `RuntimePopulation.decide(...)` before using a field.
- **Evidence:** a number reaches a result only as an `AdmittedClaim`. Prompts state rules; code
  enforces them.
- **Deep Research:** a finding is a quote in a captured source or nothing; every query and fetch
  leaves through `RetrievalGate`.
- **New hot-path behaviour** ships behind a kill switch, off in test, its cost measured.
- **Frozen inputs:** never edit a golden fixture to make a test pass; never hand-edit
  `legacy/npc-panel-18.6.6/app/` (regenerated by `AIA-reference/tools/extract_legacy.py`).
- **No secrets and no real client data** in code, logs, fixtures, artifacts or commits.

**Stack:** Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic, PostgreSQL 16, Next.js 16,
React 19, TypeScript, Tailwind 4. AWS (develop: one EC2 host under Docker Compose with S3,
Cognito, ECR, SSM, Bedrock; ADR 0009). Terraform, GitHub Actions with OIDC. No Kubernetes, Redis
or SQS (ADR 0002).

## 4. Planning

A feature's plan and status live in `.planning/plans/<feature>.md`, with front-matter:

```markdown
---
status: in-progress        # planned | in-progress | done
chunks:
  - "[x] 1. …"
  - "[ ] 2. …"
---
```

Write the plan before a large change and tick chunks as they land. Size the chunks as you see
fit. `python tools/progress.py --check` validates the front-matter.

**Anchor claims about code** with `file:line @ SHA` or a test name when you write them into a plan,
an open item or a PR. An anchored claim can be checked with one `git show`; an unanchored one is a
hypothesis. A defect filed in `open-items.md` states the claim, the anchor, a reproduction, the
user-visible consequence, the smallest fix and the test that would have caught it.

## 5. Git

**What you may do on your own:** create a branch from a fresh develop
(`git fetch origin develop && git checkout -b <prefix>/<slug> origin/develop`), commit, push it,
and open a **draft** pull request into `develop`. Commit early and often so work never dies in a
container. Mark it ready for review when it is green and you are satisfied.

**What needs the product owner's word:** merging into `develop` or `main` (except artifact exports
below), force-pushing or rewriting someone else's branch, anything that changes AWS or another
outside system, and anything destructive or hard to undo. A PM coordinator session may relay his
word, quoting it and the time.

**Artifact exports** (files under `prototypes/` or `tools/build_map/` only) may be merged without
asking once CI is green and Codex is clean on the head, with a merge commit.

**Never touch the working tree to look at another ref.** Read it: `git show origin/main:path`,
`git diff origin/main -- path/`, or `git worktree add /tmp/check origin/main`. Never
`git checkout <ref> -- .`, and use `git stash` or `git reset --hard` only to undo, not to inspect.

**Branches:** `main` (release) ← `develop` (integration; every green head deploys to
<https://aia-develop.art-chain.io/>) ← `feature/<slug>`, `fix/<slug>`, `chore/<slug>`. Never commit
directly to `main` or `develop`. Merge `origin/develop` into a long-lived branch before pushing.

**Commits:** imperative mood, plain English, describing the change's effect (no `type(scope):`
prefix). The body says why: what was wrong, why the obvious fix isn't the fix, the trade-off, and
any numbers measured. Each commit builds and passes on its own. Author: the person whose account
the work comes from (`nigelblount <nigelblount@art-chain.io>`, or
`Aram Bahbouh <aram.bahbouh@art-chain.io>`), with the session's `Co-Authored-By:` and
`Claude-Session:` trailers.

**Pull requests:** the body is the commit body widened: the problem, the approach, the trade-off,
what you measured, what you deliberately did not do. Green on the blocking checks in
[ARCHITECTURE.md §8](ARCHITECTURE.md#8-ci-tiers) before review.

## 6. Tests and quality

- **A change is proven by a test** that fails before it and passes after it.
- **Never skip, disable, quarantine or loosen a test to get green.** A failing test is a finding.
- **Flakes are defects.** The usual cause is parallel tests mutating global state; fix it by making
  the mutating test non-parallel, not with a retry or a sleep. Size timing budgets generously.
- **Mocks live at interface boundaries**, through the protocol. No real third-party HTTP in tests.
- **Keep the diff lean:** reuse before writing new code, leave no dead code.
- **Review before merge:** run `/code-review` (and `/security-review` when the change touches
  scope, permissions, secrets, egress, input parsing or infra). A P1 or P2 finding blocks the merge.
- Domain logic that ports 18.6.6 behaviour: run the parity suite locally (`make test-parity`); CI
  can't.

**Known flakes** (add one the moment it's confirmed: symptom, confirmation, cause, fix):

- `apps/web` jsdom component tests time out (5 s) or a `findBy*` misses only on a loaded host. Cause:
  CPU starvation, no shared state. Fix: testTimeout 30 s (`apps/web/vitest.config.mts`),
  asyncUtilTimeout 10 s (`apps/web/vitest.setup.ts`) (#536, OI-134).
- `ReportDocumentView.editor.test.tsx` › "approves koncept 1 nothing when an edit starts…" failed
  once on a loaded host; same cause as above, no fix yet.

## 7. Before you call it done

`make verify` (typecheck, layer_check, exposure_check, format check, tests, web_design, web_unused,
test-web) is green; the plan file reflects what landed; docs you made stale are updated; and you
can state the trade-off in one sentence.

Report outcomes faithfully: if tests fail, say so with the output; if you skipped a step, say which
and why; when something is done and verified, say so plainly.
